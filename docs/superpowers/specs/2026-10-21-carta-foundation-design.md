# Carta 2 — фундамент: роли, столы, подписка, регистрация

Дата: 2026-10-21. Статус: в работе. Владелец делегировал решения («просто делай»); всё ниже — решения исполнителя, кроме помеченного «владелец».

## Зачем

Аудит 2026-10-21 показал: цифровое меню красиво читается, но это не продукт, который ресторан купит сам. Нет самостоятельной регистрации и оплаты, нет понятия «стол», нет сотрудников. Без этого нельзя построить ни вызов официанта, ни заказ. Владелец: строим Carta заново, старое берём только если подходит; Screen и Casa не трогаем.

## Цели

- Ресторан проходит путь «регистрация → меню → столы → QR на столах → оплата» без участия Nasim.
- У каждого стола свой QR; меню знает, за каким столом гость.
- Права определяются базой (роли), а не почтой, вписанной в код.
- Подписка на заведение с триалом 14 дней без карты, оплата через Stripe.

## Не цели (сейчас)

- Заказ и оплата счёта со стола — только после связки с кассой (RKSV). «Rechnung bitte» будет вызовом официанта.
- Аналитика для владельца, мультиэкран Screen, поддомены `slug.oriz.at`.
- Переписывание Screen и Casa.

## Анти-цели

- Номер стола в QR открытым текстом (`?t=8`): тогда «вызвать официанта к столу 8» можно из дома.
- Ссылка «Поделиться» из меню, несущая код стола.
- Своя платёжная форма и свой биллинг вместо Stripe Checkout / Customer Portal.

## Данные (миграция 0016)

- `platform_admins(user_id)` — супер-админы (Nasim). Функция `is_platform_admin()`.
- `venue_members(venue_id, user_id, role)` — `owner | manager`. Заполнена из `venues.owner_id`. Функция `is_venue_member(venue_id)` (включает платформенных админов). Политики RLS «member» на `venues` (update), `sections`, `items`, `menus`, `venue_events`, `screen_settings` — рядом со старыми `owner_id`-политиками; старые удаляются, когда уйдёт старая админка.
- `venue_tables(id, venue_id, label, zone, code, is_active, position)` — код из 8 символов алфавита без похожих знаков (`23456789ABCDEFGHJKMNPQRSTUVWXYZ`), уникален глобально. Публичного чтения нет; гость получает стол через `resolve_table(code)` (security definer) — возвращает только slug, id и название стола.
- `subscriptions(venue_id, plan, status, trial_ends_at, current_period_end, cancel_at_period_end, stripe_customer_id, stripe_subscription_id)` — `status`: `trialing | active | past_due | canceled | comped`. Существующие заведения → `comped` (демо и тестовые, бесплатно). Читать могут участники; пишет только сервер (webhook Stripe).
- `billing_events(id, type, payload)` — журнал событий Stripe для идемпотентности, без публичных политик.
- `venues.plan` больше не источник правды; остаётся, пока его читает старый код.

Сотрудники (официанты) — **устройства**, не аккаунты: таблица `staff_devices` появится на этапе «вызов официанта» (привязка телефона по QR из админки, push / Telegram).

## Гостевой вход со стола

`/t/<code>` → сервер вызывает `resolve_table` → ставит cookie `oriz_table` (код, 3 часа) → редирект на чистый `/<slug>`. Меню читает cookie, проверяет, что стол принадлежит этому заведению, и показывает «Tisch 8». Ссылка «Teilen» остаётся чистой. Неизвестный или выключенный код → обычное меню без стола (если заведение известно) или 404.

## Новая админка `/app`

Нейтральный дизайн (не в цветах ресторана), mobile-first, немецкий интерфейс без смешения с английским. `/app` → список заведений участника (одно → сразу внутрь). `/app/<slug>` — обзор; `/app/<slug>/tische` — столы: добавить один, добавить сразу N, переименовать, зона, выключить, удалить, «neuer Code» (старая наклейка перестаёт работать), печать листа наклеек A4. QR генерируется у нас на сервере (пакет `qrcode`, SVG), а не через внешний `api.qrserver.com`.

Старая `/admin` живёт, пока `/app` не покроет редактирование меню, профиль и Screen.

## Порядок этапов

1. **Фундамент** (эта спека, этап 1): миграция 0016, общий модуль прав `src/lib/auth.ts` вместо почты и списков демо в каждом маршруте, `/app` со столами и печатью, `/t/<code>`.
2. **Регистрация**: `/registrieren` (почта + пароль, подтверждение), мастер: название → адрес ссылки (проверка, запрещённые слова) → меню (вставить текст парсером / вручную) → стиль → столы → готово. Триал 14 дней.
3. **Stripe**: Checkout + Customer Portal + webhook → `subscriptions`; письма о конце триала; что видит гость при неоплате. *Нужно от владельца:* аккаунт Stripe, цены тарифов, Vercel Pro, AGB/Impressum.
4. **Вызов официанта**: кнопки у гостя (Bestellen / Rechnung / Frage), `staff_devices`, экран «Service» для стойки, web push, Telegram, «кто принял — тот идёт».
5. **Новое гостевое меню**: одна основа + три оформления; поиск, аллергены ЕС списком, размеры/варианты цены, честные фильтры.
6. **Новая админка меню** в `/app`: разделы, блюда, переводы, «ausverkauft» в один тап; затем удаление старой `/admin`.

## Безопасность перед этапом 2 (от сессии «Аудит безопасности», 2026-10-21)

Саморегистрация делает любого незнакомца «authenticated», поэтому до открытия `/registrieren`:
- `venues`: участник не должен менять `plan`, `ai_credits_used`, `owner_id`, `slug`, `custom_domain` (и `logo_svg` без санитизации) — запрет по колонкам или триггер; тариф берётся только из `subscriptions`.
- Убрать INSERT в `venues` / `casa.properties` для обычных пользователей (старая политика «owner all venues» с `with check owner_id = auth.uid()`): заведение создаёт только сервер в мастере регистрации.
- `casa leads auth read` (`using true`) — закрыть, сейчас любой вошедший видит все лиды.
- Отозвать у `anon` прямые INSERT/UPDATE/DELETE на `subscriptions`, `billing_events`; `is_platform_admin()` / `is_venue_member()` оставить исполняемыми (их зовут RLS-политики), `find_user_id_by_email` — убрать захардкоженную почту.
- `/api/admin/venue-profile` (весь body в update) и `/api/admin/casa/property-update` (slug/logo_svg) — белый список полей.

**Сделано 2026-10-21 (миграция 0018_signup_lockdown):** INSERT/DELETE в `venues` и `casa.properties` — только платформенный админ (или сервер); триггеры `venues_guard` / `casa.properties_guard` не дают участнику менять slug, owner_id, plan, ai_credits_*, custom_domain, logo_svg, logo_url; `casa.leads` читает только платформенный админ; запись в `subscriptions`, `billing_events`, `platform_admins`, `venue_members` — только сервер; `increment_ai_credits` — только service_role; `find_user_id_by_email` проверяет `is_platform_admin()`. Триггер `venues_sync_owner`: смена `venues.owner_id` (старая админка) обновляет `venue_members`, новое заведение сразу получает подписку `trialing` на 14 дней. Маршруты `venue-profile` и `casa/property-update` — белый список; `/auth/callback` больше не уводит на чужой сайт.

## Этап 2 — регистрация (сделано 2026-10-21)

- `/registrieren`: почта + пароль (мин. 8), Supabase `signUp` с подтверждением письма → `/auth/callback?next=/app/neu`. Одно и то же сообщение, был ли адрес уже зарегистрирован.
- `/app` без заведений → `/app/neu`: название + адрес (`src/lib/slug.ts`: транслитерация умлаутов, 3–40 символов, список зарезервированных имён, живая проверка занятости). Одно заведение на аккаунт в самообслуживании (платформенный админ — без лимита). Создание — серверное действие через service role, остальное делает триггер.
- `/app/<slug>/start?schritt=speisekarte|stil|tische|fertig`: вставить текст меню (тот же парсер, что у импорта супер-админа; текст под блюдом пишется в `items.description`, его показывают все три вида меню) → вид (classic / visual / modern) и цветовой пресет с живой превью в iframe → число столов → «готово» (ссылки на меню, печать QR, обзор). Любой шаг можно пропустить; обзор показывает «Einrichtung fortsetzen», пока в меню нет блюд.
- Не проверено вживую: клик по ссылке из письма подтверждения (нужен доступ к ящику). Для настоящих клиентов в Supabase нужны свой SMTP и `https://www.oriz.at/auth/callback` в списке Redirect URLs.

## Этап 4 — вызов официанта (сделано 2026-10-22, миграция 0019_service_calls)

- Данные: `venues.service_calls_enabled` (по умолчанию выключено), `staff_devices` (имя, хэш токена устройства, push-подписка, `revoked_at`), `staff_pairings` (одноразовый код привязки, 10 минут), `service_calls` (стол, снимок названия стола, `order | bill | help`, `open → accepted → done`, или `cancelled` гостем; хэш секрета гостя). RLS включён, клиентских политик нет — всё через сервер.
- Гость: кнопка «Service» над нижней панелью меню, только если гость пришёл по QR стола и функция включена. Стол берётся только из httpOnly-cookie `oriz_table`, не из запроса. Повторное нажатие того же вида не создаёт второй вызов; лимит — 6 вызовов на стол за 10 минут. Статус видно по id (UUID), отменить может только тот, у кого секрет. Тексты DE/EN по языку меню.
- Персонал: `/app/<slug>/service` — включить, «Gerät verbinden» (QR/ссылка на `/s/<код>`), «Dieses Gerät verwenden», список устройств с «Trennen». Устройство = cookie `oriz_staff` на год (в базе только хэш). `/service` — тёмный экран: открытые вызовы, «Übernehmen» (кто первый — тот идёт, условный UPDATE), «Zurückgeben», «Erledigt», «Zuletzt»; опрос каждые 3 с (15 с в фоне), звук, вибрация, «Bildschirm wach halten».
- Push: свой код без зависимостей (`src/lib/web-push.ts`, VAPID + aes128gcm по RFC 8291, сверено с тестовым вектором RFC байт в байт), service worker `/service-sw.js`, манифест `/service.webmanifest` (на iPhone push работает только из приложения на домашнем экране). Ключи `NEXT_PUBLIC_VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY`. Доставка на реальный телефон не проверена — встроенный браузер блокирует уведомления.
- Не сделано: Telegram (нужен токен бота от владельца), звук/вибрация на заблокированном экране без push.

## Этап 5 — новое гостевое меню (сделано 2026-10-22, миграция 0020_price_variants)

- Одна основа: `src/components/guest/GuestMenu.tsx` (язык, меню дня, поиск, фильтры, живые обновления, карточка блюда, легенда аллергенов, подвал) + `looks.tsx` (Classic / Modern / Visual рисуют только шапку, заголовок раздела и блюда). `MenuView` — тонкая обёртка. Старые `MenuView{Modern,Visual}`, `ItemRow`, `SectionBlock`, `MenuItemCardVisual`, `ItemDetailModal`, `AllergenIcons`, `menu-filters` удалены.
- Данные — `src/lib/guest-menu.ts` (чистый, тесты): аллергены из букв A–R и из слов («Gluten, Ei», «Krustentiere») → коды; пусто = «нет данных», «–» = «нет 14 аллергенов». Все 80 реальных значений из базы распознаются. Диет-метки — только явно поставленные (`vegan` ⇒ `vegetarisch`). Текст под блюдом = `description`, иначе `ai_caption`; перевод заменяет его; длинный `ai_caption` рядом с описанием — «история» только на немецком.
- Поиск без учёта регистра, акцентов и умлаутов (Käse = Kaese = kase), все слова должны встретиться; появляется от 8 блюд.
- Честные фильтры: «Vegetarisch / Vegan» — только если хоть одно, но не все блюда помечены; «Ohne <аллерген>» — только если аллергены указаны хотя бы у 40% блюд; блюда без данных при этом скрываются с пометкой «N Gerichte ohne Allergenangaben ausgeblendet · Trotzdem zeigen». Фильтр «Alkohol» (угадывал по названию раздела и прятал воду) и метка «Glutenfrei» убраны.
- Варианты цены: `items.price_variants` jsonb `[{label, price_cents}]`; в списке столбиком, в Visual «ab X», в карточке таблицей. `price_cents` = минимальный вариант (для Screen, печати, старой админки). Владелец вводит «0,3 l 3,90; 0,5 l 4,90» в старом редакторе блюда; сервер проверяет.
- Нулевая цена не печатается. В подвале только реально заданные ссылки. Легенда букв аллергенов внизу меню (как требуют австрийские правила).
